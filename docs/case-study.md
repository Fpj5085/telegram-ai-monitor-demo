# 项目案例：Telegram 信息监控与微信交付

## 项目定位

这是一个个人使用的 Telegram 信息自动化系统：从经过白名单选择的公开频道采集信息，经过本地规则与 AI 辅助判断，生成日报或实时告警，再通过微信机器人交付。目标是把分散的信息筛选和定时查看，变成可持续运行、可追踪并能从发送故障中恢复的流程。

本仓库是该系统的**公开脱敏演示**。这里的频道、消息、告警和微信 HTTP 服务全部是模拟内容；它不是原生产项目的代码镜像，也不声称本地 Demo 产生过历史生产结果。

**贡献边界：** 本仓库的离线模拟器与本轮展示文档由 AI 助理协助搭建，不能作为“本人独立编写这份 Demo”的证据。能从既有项目约束和历史任务记录支持的个人贡献，是实际系统的需求拆解、运行边界、故障恢复策略、改动范围决策和验收推动；原系统代码应表述为 AI Coding Agent 辅助实现、本人负责工程决策与验收，不能笼统宣称全部代码由本人独立手写，也不能反过来说项目只是 AI 自动完成。

## 原系统的历史功能范围

下列范围来自既有项目交接记录和仓库操作说明，表示系统曾实现/部署过的设计，不表示当前仍在线：

- 对配置的 Telegram 公开频道进行采集；一个 `listen` 进程独占 Telethon Session 并写入 SQLite。
- 日报任务从 SQLite 读取，不另起 Telethon 客户端；按本地计划任务生成并通过微信机器人交付。
- 实时规则筛选机会类消息；中等置信候选可由模型复核，最终进入持久化告警队列。
- 使用 Windows 计划任务分别调度日报和实时监听，并围绕启动、代理、日志和队列状态进行运维。
- 微信下行曾遇到会话失效返回业务错误 `-2`，触发了“熔断、保留日报与队列、版本变化后恢复”的可靠性改造。

原系统技术路线包括 Python、Telethon、SQLite、PowerShell/Windows Task Scheduler、微信本地接口，以及配置的模型服务。公开 Demo 刻意只依赖 Python 标准库，不复用真实配置或运行数据。

## 项目负责人主导的工程决策

本项目的个人贡献应表述为真实的产品与工程责任，而不是“独立手写所有代码”：

- **定义自动化边界：** 明确频道白名单、单一 Telethon Session 所有者、日报只读 SQLite 等约束，避免重复登录与无界采集。
- **推动故障闭环：** 发现微信业务错误 `-2` 后持续重试的风险，要求以运行文件的修改时间和大小构造非敏感版本号，并把熔断状态持久化；检查版本时不读取凭据内容。
- **设计恢复顺序：** 指定只有文件元数据变化后才允许恢复；先重发数据库中已保存的日报，再按每分钟最多一条处理积压告警；不得删队列或重新调用模型来“修复”发送。
- **定义验收和运维护栏：** 要求跨进程/重启验证、离线故障注入、测试后只保留一个 Telethon 监听实例，并要求交代测试、运行状态和回滚点。
- **使用 AI Coding Agent：** AI 辅助了部分 Python 实现、测试和文档修改；项目负责人负责提供真实业务约束、确定行为取舍、反馈运行问题、批准改动范围并验收结果。不要把 AI 辅助实现改写成“全部代码由本人独立完成”。

| 工作内容 | 个人负责 | AI Coding Agent 辅助 |
|---|---|---|
| 目标与边界 | 确定业务链路、频道/数据限制、发送节奏和安全要求 | 帮助整理为可执行的实现与测试清单 |
| 故障决策 | 识别 `-2` 无限重试的影响，选择持久熔断与分阶段恢复策略 | 分析代码路径并实现部分改动 |
| 验收与运行 | 设定验收条件、审查测试回执、决定是否恢复单一监听任务 | 执行测试、汇总结果并协助准备变更说明 |
| 公开演示 | 决定只展示合成数据与模拟接口 | 生成本仓库的脱敏 Demo 初稿、文档和离线测试 |

## 核心工程难点

1. **单会话所有权与任务隔离：** 让一个监听进程拥有 Telethon Session，日报仅从 SQLite 读取，降低会话争用和重复采集风险。
2. **业务错误熔断：** 把微信业务错误 `-2` 与一般失败区分；对同一运行文件版本持久化熔断，跨进程启动仍能快速阻断请求。
3. **受控恢复：** 把会话文件元数据变化作为恢复门槛，优先发送已保存日报，不重新生成日报或调用模型。
4. **积压限速：** 将历史告警保留在 SQLite 队列，通过持久化节流实现每分钟最多尝试一条，而不是故障恢复后突发发送。
5. **可验证性与脱敏：** 用离线 fixture 和本地假接口展示故障路径；真实 Session、频道正文、微信凭据和运行数据库不进入公开仓库。
